### PPT 的故事现在已经可以非常稳定地讲

不要从“我们用了几个 Agent”开始，而应该从一个矛盾开始：

> **为什么现有 Agent Team 每接一个新任务，都像一支没有组织记忆的临时团队？**

然后指出：

```Plain Text
Fixed Roles
Fixed Team
Fixed Workflow
Task Ends
Experience Disappears
```

接着把比赛要求往核心上收：

```Plain Text
Multi-Agent 只是基础
Self-Evolution 才是核心
```

然后明确：

> **Retry ≠ Evolution**

再用“公司”类比把老师带进来：

```Plain Text
Task       = 项目
Agent      = 员工
Role       = 岗位
Skill      = 专业能力
Team       = 项目组
Strategy   = 组织方法
Experience = 组织经验
Evolution  = 组织调整
```

这时再正式提出 EvoTeam：

> **我们不是只构建一支 Agent Team，而是让这支 Team 根据经验学会如何重新组织自己。**

随后进入核心技术抽象：

```Plain Text
Strategy =
Role
+ Skill
+ Tool
+ Prompt
+ Team Topology
+ Execution Policy
```

然后讲完整闭环：

```Plain Text
Task
 ↓
Strategy
 ↓
Team
 ↓
Run
 ↓
Evaluation
 ↓
Experience
 ↓
Attribution
 ↓
Mutation
 ↓
Validation
 ↓
Next Generation
```

整套 PPT 最值得反复出现的三句话已经可以固定：

> **任务决定初始组织。**  
> **证据决定问题归因。**  
> **验证决定组织是否换代。**

最后再用实验回答“凭什么相信你们真的进化了”：

```Plain Text
Single Agent
vs
Fixed Multi-Agent
vs
Dynamic Team
vs
EvoTeam
```

以及：

```Plain Text
Before
vs
After
```

这样 PPT 的逻辑就不是“功能介绍”，而是：

```Plain Text
问题
→ 洞察
→ 机制
→ 创新
→ 可信性
→ 实验验证
```

这会强很多。

### 总架构图也基本定型了

最适合放 PPT 的不是复杂软件工程图，而是四层：

```Plain Text
┌─────────────────────────────────────────────┐
│             Evolution Console               │
│                                             │
│ Task / Strategy / Team Graph / Trace        │
│ Evaluation / Evolution / Generations        │
└─────────────────────┬───────────────────────┘
                      │
┌─────────────────────▼───────────────────────┐
│               EvoTeam Core                  │
│                                             │
│ Task Analyzer                               │
│ Strategy Library / Router                   │
│ Team Orchestrator                           │
│ Evaluator                                   │
│ Experience Store                            │
│ Failure Attribution                         │
│ Mutation Planner                            │
│ Validation Gate                             │
│ Strategy Registry                           │
└─────────────────────┬───────────────────────┘
                      │
┌─────────────────────▼───────────────────────┐
│        Runtime Abstraction / Adapter        │
└─────────────────────┬───────────────────────┘
                      │
┌─────────────────────▼───────────────────────┐
│            openJiuwen Core                  │
│ Agent / Model / Tool / Workflow / Runtime  │
└─────────────────────────────────────────────┘
```

这张图有一个非常重要的答辩作用：

> **它直接告诉评委 openJiuwen 做什么、EvoTeam 做什么。**

不会出现“你们是不是把 openJiuwen 自带能力包装了一遍”的疑问。

---

而我认为 **PPT 中真正应该画精美的，不是一张图，而是 5 张关键图**：

```Plain Text
① EvoTeam / openJiuwen 四层架构

② Strategy Family
   Base → News / Academic
   Specialization / Generalization

③ Experience
   Event → Run → Evolution Window

④ Failure Attribution
   Rule + Trace + LLM → Mutation Scope

⑤ Evolution
   Candidate A/B/C
       ↓
   Validation Gate
       ↓
   Promote / Reject
```

尤其第 ⑤ 张：

```Plain Text
Current Strategy ─────┐
                      │
                      ▼
                Validation Set
                      ▲
                      │
Candidate Strategy ───┘
                      │
                      ▼
          Quality / Cost / Latency
              / Complexity
                      │
            ┌─────────┴────────┐
            ↓                  ↓
         Promote             Reject
```

我认为它会是整套 PPT **最重要的一张图之一**。

因为它一眼就解释了为什么我们的“自演进”不是 LLM 自己瞎改自己。

---

还有一个现在已经非常明确的产品亮点：

# Evolution Governance

我们不是单纯说：

> “系统能自动进化。”

而是：

```Plain Text
为什么变？
依据是什么？
改了什么？
有哪些 Candidate？
验证表现怎么样？
为什么上线？
为什么拒绝？
能不能回滚？
什么时候冻结？
```

这个概念我建议正式保留。它同时解决了**可解释、可验证、可回滚、可展示**四个比赛问题。

现在产品机制已经足够稳定，下一步可以真正进入 **PPT 视觉设计阶段**了：先把这 5 张核心图和 20 页左右的故事骨架设计出来，再决定哪些页需要精简成最终汇报版本。
