# 二、为什么一定要这样分？

假设你直接写：

```Python
planner = JiuwenAgent(...)
executor = JiuwenAgent(...)
critic = JiuwenAgent(...)
```

然后 Strategy 就保存这几个对象。

初期当然能跑。

但过一阵子你要做：

```Plain Text
Strategy v1
vs
Strategy v2
```

就会遇到问题：

- 怎么序列化？
- 怎么版本化？
- 怎么保存数据库？
- 怎么 Diff？
- 怎么把 Candidate 放进沙箱？
- 怎么回滚？
- 怎么单元测试而不调用模型？
- 将来 openJiuwen API 变了怎么办？

所以你们需要自己的“设计图”。

例如：

```Python
class AgentConfig(BaseModel):
    id: str
    role: RoleType
    prompt_ref: str
    skill_refs: list[str]
    tool_refs: list[str]
    model_ref: str
```

这是：

> **EvoTeam 对 Agent 的抽象定义。**

然后：

```Python
class Strategy(BaseModel):
    id: str
    version: int
    agents: dict[str, AgentConfig]
    edges: list[Edge]
```

这是：

> **EvoTeam 对组织策略的抽象定义。**

最后才有：

```Python
class OpenJiuwenRuntime:
    def create_agent(self, config: AgentConfig):
        return JiuwenAgent(
            prompt=...,
            tools=...,
            model=...,
        )
```

这叫：

> Adapter。

# 七、1. Orchestrator 到底是谁？

## What

它是：

> **在线运行控制器。**

不是 Agent。

## Who

主要由：

```Plain Text
确定性 Python 代码
```

实现。

## Why

因为 Strategy 只是设计图：

```Plain Text
Planner → Executor → Critic
```

但还需要有人真的：

- 创建 Agent；
- 把 Planner 输出给 Executor；
- 控制并发；
- Retry；
- Timeout；
- Budget；
- 收 Trace。

这个就是 Orchestrator。

## When

**每一次 Task 都会工作。**

## How

```Plain Text
Task
 ↓
读取 Current Strategy
 ↓
实例化 Agent
 ↓
按照 Topology 调度
 ↓
收集结果
 ↓
形成 Run
```

简单代码：

```Python
class Orchestrator:

    async def execute(self, task, strategy):

        team = self.build_team(
            task,
            strategy,
        )

        result = await self.run_team(team)

        return result
```

# 八、2. Critic 是谁？

Critic 和前面其他几个完全不一样。

## What

> **业务 Agent。**

它属于：

```Plain Text
Team
```

## Who

一般由：

```Plain Text
LLM Agent
```

实现。

可能调用 Tool。

## Why

它负责：

> 当前任务内部的质量控制。

例如 Executor 给出：

```Plain Text
项目计划草稿
```

Critic 检查：

```Plain Text
有没有遗漏？
有没有明显矛盾？
要不要返工？
```

## When

Task 还在执行过程中。

例如：

```Plain Text
Planner
 ↓
Executor
 ↓
Critic
 ↓
发现问题
 ↓
Executor Retry
```

注意：

> **Critic 不是给 Strategy 打分的。**

它只是想把**当前这道题做好**。

# 九、3. Evaluator 是谁？

这是第一个特别容易跟 Critic 混的。

## What

> **单次 Run 的系统级评分器。**

## Who

可以是混合的：

```Plain Text
规则
+
确定性程序
+
LLM Judge
```

例如项目规划：

```Plain Text
资源冲突
→ Python 检查

依赖有环
→ Graph Algorithm 检查

计划质量
→ Rubric / LLM Judge
```

## Why

Critic 的目标：

> 把答案改好。

Evaluator 的目标：

> **客观记录这次到底表现多少分。**

## When

任务已经结束之后：

```Plain Text
Run Finished
 ↓
Evaluator
```

## How

输出：

```Python
RunMetrics(
    quality=0.86,
    success=True,
    constraint_errors=0,
    tokens=8500,
    latency=12.4,
    agent_count=3,
)
```

所以：

```Plain Text
Critic
= 运动员队伍里的检查者

Evaluator
= 比赛结束后的裁判
```

# 十、4. Experience 到底是什么？

这个东西最容易被误会成一个 Agent。

不是。

## What

> **Experience 是数据。**

它不是：

```Plain Text
Experience Agent
```

至少 V1 完全不需要这么搞。

它可以包括：

```Plain Text
Trace
SealedRun
FailureExperience
ImprovementExperience
```

## Why

因为 EvolutionManager 不应该凭空说：

> “感觉最近 Executor 不行。”

必须有证据：

```Plain Text
过去 10 个 Run
4 次 resource_conflict

3 次错误首次出现在 Executor

Critic 4 次都没发现
```

这些就是 Experience。

## When

每次 Run 结束都积累。

## How

```Plain Text
Run
 ↓
Evaluator
 ↓
SealedRun
 ↓
ExperienceStore
```

所以：

> Experience 是“系统过去发生过什么”的长期事实基础。

# 十一、5. Monitor 是谁？

## What

> **Strategy 长期性能监控器。**

## Who

几乎完全是：

```Plain Text
确定性代码 + 统计规则
```

不需要做成 LLM Agent。

## Why

Evaluator 只能说：

> Task #17 得了 82 分。

它不能说：

> 最近这个 Strategy 整体是不是开始退化了？

Monitor 看的是：

```Plain Text
最近 10 次
最近 20 次
一段时间窗口
```

## When

可以：

```Plain Text
每产生 N 个 SealedRun
```

检查一次。

注意：

> 检查一次 ≠ 演进一次。

## How

比如：

```Python
if resource_conflict_count >= 3:
    trigger = True
```

或者：

```Python
if quality_mean < baseline * 0.95:
    trigger = True
```

所以：

```Plain Text
Evaluator
= 单次成绩

Monitor
= 长期趋势
```

# 十二、6. EvolutionManager 是谁？

这个名字听起来最像“大脑”，但你最好不要把它想成超级 Agent。

## What

> **Strategy Evolution 的状态机和流程控制器。**

## Who

核心：

```Plain Text
确定性 Python 代码
```

局部可以调用 LLM。

## Why

因为当 Monitor 说：

```Plain Text
Strategy 有问题
```

还需要一个模块组织后面：

```Plain Text
归因
→ 生成 Candidate
→ Validation
→ Promote / Reject
```

这就是 EvolutionManager。

## When

正常 Task 不需要它。

只有：

```Plain Text
Monitor → Trigger
```

后才启动。

## How

```Python
class EvolutionManager:

    async def evolve(self, current):

        attribution = await self.attributor.analyze(...)

        candidates = await self.generator.generate(
            current,
            attribution,
        )

        result = await self.validator.validate(
            current,
            candidates,
        )

        if result.passed:
            promote(...)

        else:
            reject(...)
```

所以：

> 它管理演进流程，但不应该自己既归因、又评分、又验证、又拍板一切。

# 十三、7. Validator 是谁？

这里也容易和 Evaluator 混。

## What

> **Strategy Candidate 的实验比较器。**

## Who

主要是确定性实验框架。

内部仍然会调用 Evaluator。

## Why

Evaluator 只能告诉你：

```Plain Text
Candidate 在 Task #1 得 89
```

但这不能说明 Candidate 好。

Validator 要做的是：

```Plain Text
Current
vs
Candidate

在同样的一批任务上
```

然后比较。

## When

只有 Candidate 出现以后。

## How

比如：

```Plain Text
Validation Set
├── task 1
├── task 2
├── ...
└── task 20
```

Validator 做：

```Plain Text
Current Strategy
跑 20 次

Candidate Strategy
也跑 20 次
```

每一次内部：

```Plain Text
Orchestrator
→ Team
→ Evaluator
```

然后汇总：

```Plain Text
Quality
Error Rate
Token
Latency
Agent Count
```

最后 ValidationGate：

```Plain Text
PASS
or
REJECT
```

# 十四、所以 Evaluator 和 Validator 的关系

这是非常重要的一条：

```Plain Text
Evaluator
= 一个 Run 的评分器
```

而：

```Plain Text
Validator
= 组织大量 Run 做 A/B 实验的人
```

Validator 内部会反复使用 Evaluator。

类似：

```Python
for task in validation_set:

    current_run = await orchestrator.execute(
        task,
        current,
    )

    current_score = evaluator.evaluate(current_run)

    candidate_run = await orchestrator.execute(
        task,
        candidate,
    )

    candidate_score = evaluator.evaluate(candidate_run)
```

然后：

```Python
compare(
    current_scores,
    candidate_scores,
)
```

# 十八、最后给你一个几乎可以直接贴到项目文档里的定义

> **EvoTeam 的运行分为在线执行和离线演进两个闭环。在线阶段，Orchestrator 根据当前 Strategy 实例化业务 Agent Team，Critic/Verifier 在任务内部负责质量控制，任务完成后由 Evaluator 对单次 Run 进行独立评分，并将 Trace、结果与指标封存为 Experience。StrategyMonitor 跨多个 Run 统计当前 Strategy 的长期表现，仅在重复失败、性能漂移或成本异常达到预设条件时触发演进。EvolutionManager 负责组织归因、候选生成和策略生命周期；Validator 则在独立验证集上反复调用同一执行与评价流程，对 Current 与 Candidate Strategy 进行公平比较，最终由 Validation Gate 决定晋级或拒绝。**

以及代码世界的最终一句话：

> **EvoTeam 自己保存 Role、AgentConfig、Strategy、Run、Experience 等领域对象；openJiuwen 不替代这些对象，而作为 Runtime，通过 Adapter 将 AgentConfig 和 Strategy 真正实例化并执行。**

这两个定义一旦冻结，我认为你们接下来就可以真正进入 **Domain Model → 接口设计 → 第一条 V0 运行链代码**，而不用再继续增加概念了。
