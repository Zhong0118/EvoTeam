# 一、先逐条回答你的 8 个问题

## 会不会不断演进，最后趋于一个固定的“分析 Agent”？

你的直觉是对的，但这里我建议我们**不要把演进设计成一条无限向前的直线**：

```Plain Text
Agent v1
→ Agent v2
→ Agent v3
→ Agent v4
→ ...
```

这最后很容易变成一个越来越臃肿的“超级分析 Agent”。

我更倾向于：

# 分支 + 收敛 + 复用 + 淘汰

例如一开始有一个基础报告 Strategy：

```Plain Text
ReportStrategy v1

Planner
Researcher
Writer
Verifier
```

后来系统做了很多灾难报告：

```Plain Text
灾难报告 × 20
```

逐渐发现：

- 时间线特别重要；
- 官方机构来源很重要；
- 多源事实核验很重要。

于是产生：

```Plain Text
ReportStrategy
      │
      ├── GeneralReportStrategy
      │
      └── DisasterReportStrategy
```

后来医学报告又产生另一支：

```Plain Text
ReportStrategy
      │
      ├── DisasterReportStrategy
      └── MedicalReportStrategy
```

但这里**不代表要新写一个 `AnalysisAgent2` 类**。

真正应该变化的是：

```Plain Text
Role Archetype
+
Skills
+
Tools
+
Prompt Policy
+
Team Graph
```

比如基础角色仍然是：

```Plain Text
Researcher
```

但灾难场景加载：

```Plain Text
official-source-search
timeline-analysis
cross-source-verification
```

医学场景加载：

```Plain Text
medical-literature-search
clinical-evidence-ranking
medical-citation-check
```

所以我们最好区分四层：

```Plain Text
Role
│
├─ Researcher
├─ Analyst
├─ Writer
└─ Verifier

Skill
│
├─ Web Search
├─ Literature Search
├─ Statistical Analysis
└─ Citation Verification

Tool
│
├─ Browser
├─ Python
├─ Search API
└─ Database

Strategy
│
└─ 决定这次怎么组合以上能力
```

这样不会出现：

```Plain Text
ResearchAgent
ResearchAgent2
ResearchAgent3
ResearchAgent4
...
```

这种灾难。

### 那演进什么时候停？

也不能无限跑。

我建议设计一个：

# Evolution Plateau

例如：

```Plain Text
连续 3 代
质量提升 < 1%

或者

Candidate 连续 3 次无法通过 Validation

或者

Evolution Budget 达到上限
```

就暂时：

```Plain Text
Freeze Strategy
```

直到：

```Plain Text
出现新的 Failure Pattern
或
任务分布发生变化
```

再重新解冻。

所以我们真正想做的是：

> **局部策略会趋于稳定，但整个 Strategy Library 会随着新任务形成分支。**

这个比“一直进化一个 Agent”合理得多。

# 经验自进化是不是很像 Memory？

是。

而且这正是一个很容易混淆的地方。

我建议明确：

# Memory ≠ Evolution

Memory 回答：

> **过去发生了什么？**

Evolution 回答：

> **根据过去发生的事，我们以后应该改变什么？**

比如 Memory：

```JSON
{
  "task": "sales analysis",
  "team": ["planner", "analyst", "critic"],
  "result": "failed",
  "failure": "numeric_error"
}
```

Evolution Experience：

```JSON
{
  "pattern": "numeric_error",
  "frequency": 7,
  "hypothesis": "missing numeric verification",
  "proposal": "add verifier",
  "validation_gain": 0.12
}
```

这个区别非常重要。

但我不建议**所有东西只存 Markdown**。

更合理的是两套：

```Plain Text
机器用的结构化记录
+
人看的文档
```

例如：

```Plain Text

  run_001.json

  exp_001.json

  report/
    v1.yaml
    v2.yaml

  evo_001.json
```

同时生成：

```Plain Text
evolutions/
  evo_001.md
```

供我们人类查看：

```Plain Text
为什么变？

Before？
After？
为什么 Promote？
```

# 可验证性确实会成为比赛最重要的点之一

我甚至会说：

> **如果我们最终作品只实现 70% 的功能，但是把演进验证做得非常扎实，可能比做 100 个功能但没有实验强很多。**

因为赛题明确要求：

```Plain Text
优化前 vs 优化后
```

所以我们必须一开始就按实验方式设计。

我建议严格分三套数据：

```Plain Text
History Set
    │
    │ 用来发现问题
    ▼
Evolution
    │
    ▼
Validation Set
    │
    │ 决定是否 Promote
    ▼
Test Set
    │
    │ 最后比赛报告
    ▼
Final Result
```

不能：

```Plain Text
在 A 任务失败
→ 针对 A 改
→ 再跑 A
→ 变好了
```

然后说：

> 我们演进成功。

这很可能只是过拟合。
