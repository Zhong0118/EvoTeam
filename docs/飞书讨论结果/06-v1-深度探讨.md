## 先说 RSI：像，但目前不要把 EvoTeam 叫 RSI

RSI 是 **Recursive Self-Improvement，递归自我改进**。比较严格的 RSI 不只是“系统发现自己表现不好，于是修改下一次策略”，而是连**负责改进自己的那套改进机制**也可以继续被改进，例如第一代系统改 Strategy，第二代开始改 Mutation Policy，第三代甚至能改“如何设计 Mutation Policy”。早期 RSI 讨论以及近期关于 bounded/open-ended self-improvement 的研究都强调了这种元层递归。([arxiv.org](https://arxiv.org/pdf/1502.06512?utm_source=chatgpt.com))

所以我们目前是：

```Plain Text
固定 Evolution Engine
        ↓
不断优化 Strategy
```

而真正更接近 RSI 会是：

```Plain Text
Evolution Engine v1
        ↓
优化 Strategy

同时
        ↓

优化 Mutation / Attribution / Search / Evaluator
        ↓
Evolution Engine v2
        ↓
继续改进自己的改进方法
```

因此我建议比赛里用：

> **受约束的跨任务自演进 / Controlled Inter-task Self-Evolution**

而不要说“我们实现 RSI”。RSI 可以放 Related Work 和 Future Work，这反而显得我们边界意识比较强。

# 关于你说的 Strategy 像 Git 分支

这个类比**很好用，但不能完全照搬 Git**。

你说：

```Plain Text

├── News
```

方向没问题。

但如果真的搞成大量独立分支，最终可能会：

```Plain Text
Report
├── Report-News-v7
├── Report-News-Politics-v4
├── Report-News-Tech-v8
├── Report-Paper-AI-v3
├── Report-Paper-Med-v2
...
```

Strategy Explosion。

我更建议：

```Plain Text
BaseReportStrategy
        │
        ├── News Delta
        ├── Academic Delta
        └── Disaster Delta
```

即：

> **父 Strategy 存共性，小分支只存差异。**

Academic 不重新复制 Planner / Researcher / Writer，而只是：

```Plain Text
Base Report
+
Literature Search Skill
+
Citation Verification
+
Academic Writing Policy
```

而你问“怎么合并”，我觉得第一版甚至**不要做 Git 那种复杂 merge**。

我们只需要一个非常自然的动作：

> **如果某个子分支的改进在多个兄弟分支上都有效，就把它上推到 Parent。**

例如 Academic 分支进化出：

```Plain Text
Source Reliability Check
```

后来测试发现 News、Disaster 也都变好，那么：

```Plain Text
Academic 特化能力
        ↓
验证其普适性
        ↓
Promotion to BaseReportStrategy
```

所以不是“合并分支”，而是：

> **特化向下分支，泛化向上提升。**

我觉得这个甚至可以成为我们 Strategy Family 的一个设计亮点。

# 你第 6 个问题非常关键：到底多久存一次 Experience？

这里我认为现在可以基本拍板了：

```Plain Text
Event = 观察单位
Task / Run = 学习单位
Window = 演进单位
```

不是每一句对话都生成一次 Experience。

假设执行：

```Plain Text
Planner started
Planner → Analyst
Analyst calls Python
Python failed
Analyst retries
Verifier checks
Task completed
```

这些全部实时记录：

```Plain Text
TraceEvent
```

它们相当于系统日志。

但只有整个 Task：

```Plain Text
SUCCEEDED
FAILED
CANCELLED
TIMEOUT
```

之后我们才：

```Plain Text
Seal Run
        ↓
总结此次任务
        ↓
生成 Structured Experience
```

例如：

```JSON
{
  "task_family": "data_analysis",
  "strategy": "data/v3",
  "outcome": "failed",
  "failure_tags": ["numeric_error"],
  "cost": 0.14,
  "latency": 38.1,
  "tokens": 12480
}
```

然后也不是一次失败立刻进化，而是：

```Plain Text
Run 1
Run 2
Run 3
...
        ↓
Evolution Window
        ↓
发现 repeated pattern
```

比如：

```Plain Text
最近 10 个 Data Run 中
numeric_error = 4
```

才触发。

这一点其实跟 JiuwenSwarm 当前设计有一些相似理念，但我们粒度准备定义得更明确。JiuwenSwarm 已经提供 Task Memory，把任务经验持久化到 experience store；Skill Self-Evolution 则会在完整调用结束后检测异常、用户纠正和 Reviewer Feedback，再生成 evolution record。(GitHub)

所以我们的区别应该继续强调：

> **不是“有 Memory”，而是从 Run 级历史里形成组织层 Strategy Mutation。**

# Validation Gate 再给你讲一次最白话的版本

假如现在公司有：

```Plain Text
Team v3
Planner → Analyst → Critic
```

这帮人最近连续把数字算错。

于是系统说：

> 我建议新招一个 Verifier。

产生：

```Plain Text
Team v4 Candidate
Planner → Analyst → Verifier → Critic
```

这时候不能老板一拍脑袋：

> 好！明天正式入职！

而应该：

> **让 v3 和 v4 做同一套模拟项目考试。**

比如 20 道没有直接拿来设计 v4 的任务。

结果：

```Plain Text
                 v3       v4

质量             82       88
数字错误率       15%       4%
成本            1.00     1.08
延迟            1.00     1.12
```

我们就说：

> 多花 8% 成本、12% 时间，质量提高明显，值得。

于是：

```Plain Text
Promote v4
```

但如果：

```Plain Text
质量      82 → 83
成本     1.0 → 1.8
延迟     1.0 → 2.0
```

那就：

```Plain Text
Reject
```

即使它“确实稍微聪明了一点”。

所以 Validation Gate 本质是：

> **新旧 Strategy 做同一套考试，提升够大、代价可接受，新人才能上岗。**

而且我现在反而不建议第一版就搞一个很花哨的：

Reward=0.73Q−0.14C−...Reward=0.73Q-0.14C-...

评委反而会问：

> 为什么是 0.73？

第一版更好解释的是：

```Plain Text
Success Rate 不下降
AND
Quality 至少提升 X%
AND
Cost 增长不超过 Y%
AND
Latency 增长不超过 Z%
```

清楚很多。

# Verifier、Evaluator、Attribution Agent，我建议正式分开

这个会解决你说“是不是要有专门测试 Agent”。

**Verifier** 是项目组里的人。例如报告写完了，Verifier 查引用；数据算完了，Verifier 再算一次。它参与完成任务。

**Evaluator** 更像比赛裁判。它不一定是 Agent，可以是 Ground Truth、规则、Unit Test、LLM Judge、指标计算器的组合。

**Attribution Agent** 更像事故调查员。任务失败以后，它判断：

```Plain Text
Planner 没规划验证？
Analyst 算错？
Tool 出错？
Verifier 漏检？
还是整个 Team 结构不合理？
```

Meta-Team 最新工作的核心困难之一正是这一点：多 Agent 的执行经验跨越多个 Agent 和通信消息，因此“究竟该改哪里”很难归因；它通过保留各 Agent 上下文和任务后协作来支持多尺度演进。(arXiv)

所以我认为：

> **Failure Attribution 很可能比“LLM 自动改 Prompt”更值得成为我们真正研究的模块。**
