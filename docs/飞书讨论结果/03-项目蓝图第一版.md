# EvoTeam Project Blueprint v0.1

> **EvoTeam — Building Multi-Agent Teams That Learn, Adapt, and Evolve.**

基于 openJiuwen 构建的自演进多智能体协作系统。

---

# 项目目标

EvoTeam 不重新实现 Agent Framework，而是在 openJiuwen Agent Core 之上构建一层：

**Dynamic Multi-Agent Organization & Evolution Engine**

系统需要解决四个核心问题：

1. 面对一个任务，应该有哪些 Agent？
2. Agent 应该如何分工和协作？
3. 当前协作结果是否足够好？
4. 根据历史失败与成功经验，下一次 Team 应该如何改变？

最终形成闭环：

```Plain Text
Task
 ↓
Task Analysis
 ↓
Team Formation
 ↓
Multi-Agent Execution
 ↓
Evaluation
 ↓
Experience Extraction
 ↓
Evolution
 ↓
Validation
 ↓
Promote / Rollback
 ↓
Next Generation Team
```

# 架构原则

## 2.1 openJiuwen 是执行底座

openJiuwen 负责：

- Agent 生命周期
- ReAct Agent 执行
- LLM 调用
- Tool 调用
- Agent Runtime
- 上下文处理
- 流式执行
- Workflow 基础能力

EvoTeam 负责：

- Agent Role 定义
- 动态 Team Formation
- Agent 调度
- 协作协议
- Execution Trace
- Evaluator
- Experience Memory
- Prompt Evolution
- Tool Policy Evolution
- Team Structure Evolution
- Candidate Validation
- Promote / Rollback
- 可解释演进

因此：

```Plain Text
EvoTeam != Agent Framework

EvoTeam
   ↓
Evolution / Organization Layer
   ↓
openJiuwen
   ↓
Agent Runtime
   ↓
LLM / Tool / Memory
```

# 为什么暂时不用 openJiuwen DeepAgent 当总控

openJiuwen 已经具备 Coordinator → SubAgent 的能力。

但 EvoTeam 的创新点之一就是：

```Plain Text
Team Formation
+
Team Coordination
+
Organization Evolution
```

如果直接：

```Plain Text

   ↓
官方 SubAgent
```

大量协作逻辑会隐藏在 openJiuwen 内部。

评委可能问：

> 这个动态分工是 openJiuwen 做的还是你们做的？

所以 MVP：

### 使用 openJiuwen ReActAgent 作为 Agent Primitive。

而：

```Plain Text
TeamOrchestrator
```

由 EvoTeam 自己实现。

未来可以增加：

```Plain Text

```

作为一种 Team Execution Strategy。

# 所有 Agent 输出必须结构化

这是一个重要开发原则。

不要：

```Plain Text
Planner：

我觉得我们首先应该……
```

直接让下一个 Agent 猜。

而应该：

```Python
class PlanResult(BaseModel):

    objective: str

    steps: list[PlanStep]

    success_criteria: list[str]

    risks: list[str]
```

Critic：

```Python
class CriticResult(BaseModel):

    score: float

    passed: bool

    issues: list[Issue]

    suggestions: list[str]

    failure_tags: list[str]
```

例如：

```JSON
{
  "score": 0.68,
  "passed": false,
  "failure_tags": [
    "missing_constraint",
    "weak_risk_analysis"
  ]
}
```

这些 failure_tags 后面就是 Evolution Engine 的输入。

# AGENTS.md 必须存在

因为本项目计划大量使用 Coding Agent 开发。

核心规则：

## Architecture Rules

1. `openjiuwen` 只能从 `evoteam/runtime/openjiuwen` 导入。
2. Core 层不能依赖 FastAPI。
3. Core 层不能依赖数据库实现。
4. Agent 之间禁止直接调用。
5. 所有 Agent 调用必须经过 TeamOrchestrator。
6. Agent 输出必须使用 Pydantic Schema。
7. 所有执行必须产生 TraceEvent。
8. Prompt 必须版本化。
9. Evolution 修改必须产生 Proposal。
10. Candidate Strategy 未通过 Validation 不得成为 active strategy。
11. 所有 Strategy 修改必须支持 Rollback。
12. 新功能必须附带测试。

## MVP Non-Goals

当前禁止主动引入：

```Plain Text
Redis
Kafka
Kubernetes
Microservices
Vector Database
RL Training
LangGraph
AutoGen
CrewAI
```

除非对应 Issue 明确要求。

原则：

> Keep the evolution logic sophisticated,  
> keep the infrastructure simple.

# 最重要的开发原则

整个项目始终遵循：

```Plain Text
Make it observable
before making it intelligent.

Make it evaluable
before making it evolve.

Make evolution reversible
before making it automatic.
```

翻成我们这个项目的话：

> **先让多 Agent 跑起来。**
> 
> **再让每一步能被观察。**
> 
> **再让结果能够被量化评价。**
> 
> **最后才让系统自己修改自己。**

否则非常容易做成：

```Plain Text
LLM
 ↓
LLM修改Prompt
 ↓
“我们自演进了”
```

这种无法证明、无法解释、无法复现的 Demo。

EvoTeam 应该追求的是：

```Plain Text
Observed
   ↓
Evaluated
   ↓
Proposed
   ↓
Validated
   ↓
Promoted
   ↓
Versioned
```

这才是整个项目真正的技术主线。
