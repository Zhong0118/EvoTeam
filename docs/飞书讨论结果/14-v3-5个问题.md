---

你现在问的这 5 个问题已经不是“术语怎么叫”的问题了，而是在决定 **EvoTeam 到底怎么运行**。我建议趁这个机会把 V1 的行为逻辑也冻结下来。

先给一个总判断：**V1 不应该“每来一个任务就让一个超级 Agent 临场想团队”，也不应该“每做完一个任务都再演进一轮”。** 更合理的是：

> **固定、可复现的 V0 起步 → 持续执行并收集证据 → 只有达到演进触发条件才离线尝试 Candidate → Candidate 验证通过才替换 Current Strategy → 稳定后停止主动探索，只监控异常。**

这其实也和 V3 现在“固定三角色基线、跨任务后再演进”的方向一致。

# 一开始到底固定三个 Agent，还是给一大堆 Role 让它自己选？

我现在明确推荐：

> **Role Pool 预先准备得稍微丰富一些，但 V0 Strategy 固定只使用三个 Agent。**

也就是同时存在这两个东西：

```Plain Text
Role Registry
├── Planner
├── Executor / Analyst
├── Critic
├── Verifier
├── Researcher
└── Writer
```

但是项目规划场景的初始 Strategy 固定：

```Plain Text
Strategy V0

Planner
   ↓
Executor
   ↓
Critic
```

也就是说：

> **Role Pool 是“可用职位库”，不是“每次任务都全部拿来自动组队”。**

为什么这样最好？

因为如果一开始就：

```Plain Text
Task
 ↓
LLM 从 10 个 Role 里随便选
 ↓
自动组 Team
```

你很快就无法回答：

> 后来的提升到底来自第一次动态组队，还是跨任务自演进？

这会直接污染实验。

所以 V1 最好是：

```Plain Text
初始：
固定 V0

后续：
历史证据
 ↓
发现缺陷
 ↓
从 Role Pool 中选择已有 Role
 ↓
生成结构 Candidate
```

例如：

```Plain Text
numeric / resource conflict
        ↓
ADD_AGENT(role=Verifier)
```

于是：

```Plain Text
V0:
Planner → Executor → Critic

V1 Candidate:
Planner → Executor → Verifier → Critic
```

这才是非常干净的“组织演进”。

## Role Pool + 固定 V0：我认为可以正式这么定

你的理解正确。

```Plain Text
RolePool
├── Planner
├── Executor
├── Critic
├── Verifier
├── Researcher
└── Writer
```

`Role` 是稳定的**职责原型**，V1 原则上：

```Plain Text
可以：
选择已有 Role
增加使用某个 Role
停止使用某个 Role

不可以：
LLM 自己创造一个新 Role
自动重写 Role 的核心职责定义
```

比如：

```Plain Text
Verifier
= “负责独立验证任务产物中的事实、数值和硬约束”
```

这个职责本身基本固定。

但是 Verifier 对应的：

```Plain Text
AgentConfig
├── prompt
├── skill
├── tool
└── model
```

是可以演进的。

初始 Strategy 则人为固定：

```Plain Text
Strategy V0

Planner
   ↓
Executor
   ↓
Critic
```

后续发现需要 Verifier：

```Plain Text
RolePool
   ↓ 取出 Verifier
生成 VerifierAgentConfig
   ↓
Strategy V1 Candidate

Planner
   ↓
Executor
   ↓
Verifier
   ↓
Critic
```

所以一定要区分：

```Plain Text
Role Pool
= 系统“有哪些职位可用”

Strategy
= 这套组织方案“实际用了哪些职位”
```

# 那会不会无限演进？2 个够了还一直测 3、4、5 个？

**绝对不能这样。**

这一点必须正式设计成：

> **Evolution 是事件触发的，不是每任务触发的。**

正常情况下：

```Plain Text
Task 1 → Current Strategy
Task 2 → Current Strategy
Task 3 → Current Strategy
Task 4 → Current Strategy
...
```

都只是运行。

只有出现类似：

```Plain Text
Repeated Failure
Performance Drift
High Cost
Low Agent Contribution
New Task Distribution
```

才进入：

```Plain Text
Evolution Trigger
```

所以不是：

```Plain Text
每做一次任务
↓
试 2 Agent
试 3 Agent
试 4 Agent
试 5 Agent
```

这当然既烧 Token 又没有意义。

---

## 更合理的是 Strategy 有“稳定期”

我建议给 Strategy 增加一种生命周期理解：

```Plain Text
Candidate
   ↓
Validated
   ↓
Current
   ↓
Stable
   ↓
监控
```

如果长期：

```Plain Text
Quality 稳定
Failure 没有重复出现
Cost 合理
Latency 合理
```

那么：

> **不演进。**

可以理解为：

```Plain Text
Strategy = FROZEN / STABLE
```

这里的 Frozen 不是彻底锁死。

而是：

> 暂时停止主动搜索，只继续观察。

例如：

```Plain Text
DataPlanningStrategy v3

过去 50 个任务：
Quality 稳定
Cost 稳定
严重失败 = 0

→ STABLE
```

以后任务直接使用 v3。

直到：

```Plain Text
突然连续出现新 failure pattern
```

或者：

```Plain Text
模型版本改变
任务分布改变
工具改变
成本明显上升
```

才：

```Plain Text
STABLE
 ↓
REOPEN EVOLUTION
```

## Strategy 生命周期：我认为现在必须加

你的认同是对的，这个会解决“是不是无限进化”的问题。

我建议简化成：

```Plain Text
DRAFT
  ↓
CANDIDATE
  ↓
VALIDATING
  ↓
CURRENT
  ↓
STABLE
```

失败分支：

```Plain Text
CANDIDATE
   ↓
REJECTED
```

或者：

```Plain Text
CURRENT
   ↓ 上线后退化
ROLLED_BACK
```

而 Stable：

```Plain Text
STABLE
  ↓
正常情况：继续用，不演进

STABLE
  ↓ 新 Failure / Drift
CURRENT / EVOLVABLE
  ↓
重新开启演进
```

其实可以把 `STABLE` 理解成：

> **当前 Strategy 已经成熟，关闭主动探索，只继续监控。**

这就是你第 2 点担忧最好的答案。

EvoTeam 不应该追求：

> “永远 Evolution。”

而应该追求：

> **需要的时候 Evolution，不需要的时候保持稳定。**



---

## 所以不是“永远进化”，而是：

```Plain Text
执行
 ↓
观察
 ↓
有问题吗？
 ├── 没有 → 继续使用 Current Strategy
 │
 └── 有
      ↓
   是否达到 Trigger？
      ├── 否 → 继续采样
      └── 是
           ↓
        Evolution
           ↓
        Candidate
           ↓
        Validation
```

这点其实非常重要。

> **一个成熟的自演进系统，应该知道什么时候“不改”。**

这甚至可以成为你们一个很好的产品思想。

## 演进触发阈值应该怎么设？

这里我建议：

> **V1：人工定义规则框架 + 基线实验校准参数。**
> 
> 不让 LLM 自己修改演进阈值。

比如我们可以有一个：

```Plain Text
EvolutionPolicy
```

里面配置：

```Plain Text
window_size = 10

repeated_failure_min_count = 3

quality_drop_threshold = 0.05

low_contribution_threshold = 0.01

cost_overrun_threshold = 0.15

max_candidates_per_evolution = 3

cooldown_runs = 10
```

这些数字不能一拍脑袋就说是“科学最优值”。

应该：

```Plain Text
开发者先给合理初值
        ↓
跑 V0 baseline
        ↓
观察指标分布
        ↓
校准阈值
        ↓
实验开始前冻结
```

这非常重要。

例如 V0 本身正常波动就是：

```Plain Text
Quality ±3%
```

那你设：

```Plain Text
下降 1% 就演进
```

肯定疯掉。

所以这里有两个东西：

```Plain Text
规则
= 人设计

具体阈值
= baseline 数据校准
```

## 时间不是“演进原因”

这一点也建议正式区分。

不要：

```Plain Text
每 10 个任务
→ 必须演进
```

而应该：

```Plain Text
每 10 个任务
→ 检查一次有没有演进信号
```

也就是说：

> **Window 是检查周期，不是 Mutation Trigger。**

比如：

```Plain Text
最近 10 Run
↓
没有明显问题

→ 不演进
```

再来 10 个：

```Plain Text
还是稳定

→ 继续不演进
```

# 那是不是需要一个最外层“超级调度 Agent”？

我建议：

> **不要。**

至少 V1 不要设计一个：

```Plain Text
Super Agent
├── 看所有历史
├── 决定组队
├── 判断失败
├── 决定演进
├── 生成 Strategy
├── 验证 Strategy
└── 决定上线
```

这样会变成：

> “一个大 Agent 控制一群小 Agent。”

然后整个系统所谓的“治理、验证、可解释”都会重新变成一个 LLM 黑盒。

---

## 更好的方案是“系统控制器 + 局部 LLM”

可以分成两个控制模块。

### 在线：Orchestrator

它不是业务 Agent。

```Plain Text
Orchestrator
├── 读取 Current Strategy
├── 创建 AgentInstance
├── 按 topology 调度
├── 传消息
├── 控制 retry
├── 控制 timeout / budget
└── 写 Trace
```

它原则上：

> **确定性代码为主。**

---

### 离线：Evolution Manager

也不必是一个传统 Agent。

```Plain Text
Evolution Manager
├── 扫描历史 Run
├── 判断 Trigger
├── 调用 Attribution
├── 请求生成 Candidate
├── 调用 Validation
└── 根据规则处理生命周期
```

其中只有某些步骤可以调用 LLM。

例如：

```Plain Text
Failure Explanation
Candidate Proposal
```

可以让 LLM 帮忙。

但：

```Plain Text
是否触发
是否满足结构约束
是否超过预算
是否 Promote
```

尽量由代码和明确规则判断。

所以：

```Plain Text
Evolution Manager
≠ Evolution Agent
```

至少核心控制权不要交给 LLM。

## Orchestrator 和 EvolutionManager 到底是什么关系？

你理解得基本准确。

它们都是**系统控制模块**，不是传统业务 Agent。

但是职责不同：

```Plain Text
在线世界：
Orchestrator
```

负责：

```Plain Text
“这次任务怎么跑？”
```

而：

```Plain Text
离线世界：
EvolutionManager
```

负责：

```Plain Text
“长期来看当前 Strategy 是否需要改变？”
```

可以这么看：

```Plain Text
                    EvoTeam Control Plane
                           │
             ┌─────────────┴─────────────┐
             │                           │
             ▼                           ▼
       Orchestrator              EvolutionManager
          在线                         离线
             │                           │
     执行 Current Strategy        管理 Strategy Evolution
```

---

## Orchestrator

确定性代码为主：

```Plain Text
class Orchestrator:
    def run(self, task, strategy):
        # 1. 根据 strategy 创建 agent instances
        # 2. 根据 topology 调度
        # 3. 转发上下文
        # 4. 控制 retry / timeout / budget
        # 5. 写 trace
        ...
```

它不做：

```Plain Text
Strategy 好不好？
要不要创建 V2？
V2 能不能晋级？
```

---

## EvolutionManager

也是确定性流程为主：

```Plain Text
class EvolutionManager:
    def process(self, strategy_id):
        # 获取 Strategy 长期表现
        # 判断是否达到 evolution trigger
        # 调用 attribution
        # 调用 candidate generator
        # 调用 validator
        # 根据 validation result 改 lifecycle
        ...
```

其中：

```Plain Text
LLM 可以参与：
失败原因解释
Candidate 提案
Prompt Mutation
```

但：

```Plain Text
是否超过阈值
是否违反预算
结构是否合法
Candidate 是否通过 Gate
```

尽量由代码判断。

# 检测 Strategy 性能，也是编排进 Team 里吗？

这里必须非常明确地区分：

> **Verifier / Critic 在 Team 里面。**
> 
> **Evaluator / Validation Gate 在 Team 外面。**

例如一个任务：

```Plain Text
Planner
 ↓
Executor
 ↓
Verifier
 ↓
Critic
```

这是业务 Team。

这些 Agent 在想办法：

> “把当前任务做好。”

---

执行结束以后：

```Plain Text
          Team Run
             ↓
       Final Output
             ↓
        Evaluator
```

Evaluator 是系统评价层。

它问的是：

> “这次 Strategy 表现怎么样？”

例如计算：

```Plain Text
Quality
Constraint Satisfaction
Token
Latency
Tool Calls
Agent Count
Retry Count
```

所以：

```Plain Text
Critic
= 当前任务中的审查者

Evaluator
= 系统级成绩评判者
```

二者不能混。

---

## Strategy 的真正 Validation 更应该是独立批处理

比如：

```Plain Text
Current Strategy v2
Candidate Strategy v3
```

进入：

```Plain Text
Validation Gate
```

然后：

```Plain Text
Validation Tasks #1...#20

v2 全跑一遍
v3 全跑一遍
```

比较：

```Plain Text
               v2       v3

Quality        82       88
Errors         12%      4%
Tokens         1.00     1.09
Latency        1.00     1.11
```

这是：

> **独立的 Strategy Evaluation Experiment**

不是：

> 再给 Team 加一个 `SuperEvaluatorAgent`。

否则候选既当运动员又当裁判了。

# Prompt 到底怎么分？Role 里的 Prompt、AgentConfig 里的 Prompt、用户 Prompt 怎么区别？

这个地方现在确实需要正式分层，不然以后“Prompt Evolution”会非常模糊。

我建议分 **4 类**。

---

## 第一类：Role Description

Role 是稳定职责定义。

例如：

```Plain Text
Role = Verifier

description:
负责独立检查任务结果中的硬约束、
数值、事实和一致性问题。
```

它确实有点像你说的：

> 枚举 + 一两句固定职责说明。

但我不建议把它理解为完整 System Prompt。

更像：

```Plain Text
RoleArchetype
├── id = verifier
├── name = Verifier
└── responsibility = ...
```

V1 原则上不演进它。

---

# 第二类：AgentConfig Prompt

这个才是我们真正说的：

> **可版本化、可演进 Prompt。**

比如：

```Plain Text
VerifierAgentConfig

role = Verifier

prompt_template_v3 = """
你负责验证 Executor 的输出。

必须：
1. 检查所有资源是否重叠
2. 检查依赖关系
3. 调用 constraint_checker
4. 输出 structured review
...
"""
```

这个 Prompt 会比较长，而且会随 Strategy Version 演进。

例如：

```Plain Text
v1:
"检查项目计划是否合理"

v2:
"逐项检查资源冲突、依赖和预算..."

v3:
"必须调用 constraint_checker，并输出 evidence..."
```

这个就是：

> **Prompt Mutation 的主要对象。**

---

# 第三类：Task / User Input

用户输入：

```Plain Text
请制定一个 6 周的软件项目计划，
团队成员有 A、B、C...
```

这个不是 Strategy 的 Prompt。

它就是：

> **Task Data**

每次都不同。

当然 Runtime 在真正调用模型时，会把它放进消息：

```Plain Text
system:
AgentConfig Prompt

user:
Task Input
```

但概念上不要混在一起。

---

# 第四类：Runtime Context

比如：

```Plain Text
Planner 的计划
Executor 上一步输出
Tool Result
Retrieved Experience
Critic Feedback
```

这些属于：

```Plain Text
AgentInstance
```

的运行时上下文。

也是动态变化的。

不是被 Evolution 永久“优化”的 Prompt 配置。

---

# 所以最终可以这样看

```Plain Text
Role
│
└── fixed responsibility
    “你是谁 / 负责什么”
             │
             ▼
AgentConfig
│
├── role_ref
├── evolvable prompt template   ← ★ Prompt Evolution
├── skills
├── tools
└── model
             │
             ▼
AgentInstance
│
├── Task Input
├── Runtime Context
├── Other Agent Messages
├── Tool Results
└── Current State
```

---

# 那 Prompt Evolution 到底改哪里？

主要改：

```Plain Text
AgentConfig.prompt_template
```

不改：

```Plain Text
用户输入
```

通常也不改：

```Plain Text
Role 本身的职责语义
```

例如：

```Plain Text
Role:
Verifier
```

一直没变。

但是：

```Plain Text
Verifier AgentConfig v1:
检查结果是否正确。

Verifier AgentConfig v2:
逐项检查资源、依赖、预算；
必须调用 constraint_checker；
输出错误类型、证据和位置。
```

这就是很标准的：

> Prompt Evolution。

# 你这 5 个问题最终可以浓缩成一套运行规则

我建议 V1 直接冻结下面这套。

```Plain Text
① 系统预定义 Role Pool

Planner
Executor
Verifier
Critic
Researcher
Writer
...


② 针对首个任务 Family 先固定 Strategy V0

Planner → Executor → Critic


③ 普通 Task 到来

Task
 ↓
Current Strategy
 ↓
Team
 ↓
AgentInstance[]
 ↓
Run


④ Run 结束

Evaluator
 ↓
Trace + Metrics + Experience


⑤ 正常情况下

继续使用 Current Strategy

不演进


⑥ 只有出现 Trigger

Repeated Failure
Performance Drift
High Cost
Low Contribution
...

才启动离线 Evolution


⑦ Evolution

Attribution
 ↓
生成少量 Candidate
 ↓
Independent Validation


⑧ Candidate 通过

Promote


⑨ Strategy 长期稳定

Stable / Frozen

停止主动搜索


⑩ 新失败 / Drift 出现

重新打开 Evolution
```

这套机制其实解决了你第 1～4 个问题的共同担忧：

> **EvoTeam 并不是时时刻刻疯狂试新团队，而是像一个组织一样：平时按现行制度工作；出现重复问题时才启动组织改进；新制度先试验，通过后才成为默认制度；成熟后保持稳定，直到新证据说明它需要再次变化。**

我觉得这一句话已经非常接近 EvoTeam 应该真正表达出来的系统行为。
