<title>v1-最后三个问题</title>

可以。现在这三个问题其实已经进入 **EvoTeam 最核心的算法设计** 了。把它们定下来之后，`PRODUCT_SPEC_V1_DRAFT` 基本就能升级成正式 V1。

我先给一个总判断：

> **Strategy Family 决定“经验应该沉淀到哪里”；Failure Attribution 决定“到底应该改哪里”；Mutation Search 决定“应该怎么改、改哪个版本”。**

三者刚好形成完整闭环：

```Plain Text
Task
  ↓
Strategy Family / Variant
  ↓
Run
  ↓
Evaluation
  ↓
Failure Attribution
  ↓
Evolution Trigger
  ↓
Mutation Search
  ↓
Candidate Strategy
  ↓
Validation
  ↓
Promote / Reject
  ↓
更新 Strategy Family
```

---

# 一、Strategy Family：什么时候分支，什么时候泛化？

我觉得我们之前用 Git Branch 类比是对的，但现在可以进一步修正成：

# Base Strategy + Variant Delta

不要理解成：

```Plain Text
ReportStrategy-v1
├── 完整复制一份 NewsStrategy
├── 完整复制一份 PaperStrategy
├── 完整复制一份 MedicalStrategy
```

而是：

```Plain Text
BaseReportStrategy

Planner
  ↓
Researcher
  ↓
Writer
  ↓
Verifier
```

然后：

```Plain Text
NewsVariant
+
freshness_check
+
web_search
+
timeline_verify
```

```Plain Text
AcademicVariant
+
paper_search
+
citation_check
+
academic_writer_policy
```

所以真正执行的时候：

```Plain Text
Effective Strategy
=
Parent Strategy
+
Variant Delta
```

这会非常重要，因为未来 Parent 升级后：

```Plain Text
BaseReport v3 → v4
```

News、Academic 默认都能继承。

---

## 第一次遇到一个新需求，要不要马上永久创建分支？

我建议：

**不要。**

这是我想特别修正你前面“新闻变论文，那肯定新开分支”的一点。

因为假设用户只做过一次：

> 给我分析一篇医学论文。

如果立即：

```Plain Text
MedicalResearchStrategy
```

永久入库，

很快就会产生：

```Plain Text
MedicalPaper
MedicalNews
MedicalData
FinanceNews
FinanceReport
FinancePaper
...
```

分支爆炸。

所以 V1 应该有一个非常重要的中间状态：

# Ephemeral Variant

也就是**临时特化策略**。

```Plain Text
新任务
 ↓
现有 Parent 不完全匹配
 ↓
临时生成 Variant
 ↓
只用于当前 Run
```

例如：

```Plain Text
BaseReport
+
paper_search
+
citation_check
```

先跑。

---

## 临时 Variant 什么时候升级成永久 Strategy Branch？

建议必须满足“重复需求 + 性能证据”。

例如：

```Plain Text
过去 20 个 Report Task

其中：
Academic-like Task = 6
```

而且发现：

```Plain Text
BaseReport:
Academic score = 71

Academic Variant:
Academic score = 84
```

这时候才：

```Plain Text
Ephemeral Academic Variant
        ↓
Promotion
        ↓
Persistent AcademicStrategy
```

所以我建议定义三个阶段：

```Plain Text
AD_HOC
  ↓
CANDIDATE_VARIANT
  ↓
PERSISTENT_VARIANT
```

这会非常好用。

---

# 分支 Trigger 到底看什么？

不能只看：

> “任务描述里出现 academic。”

应该看一个结构化：

# Task Signature

例如：

```JSON
{
  "family": "report",
  "domain": "academic",
  "needs_search": true,
  "source_type": "paper",
  "freshness_sensitive": false,
  "needs_citation": true,
  "needs_numeric_analysis": false,
  "risk_level": "medium"
}
```

然后一个 Strategy Variant 也有：

```JSON
{
  "family": "report",
  "supports": {
    "source_type": ["paper"],
    "needs_citation": true
  }
}
```

Router 实际做的是：

```Plain Text
Task Signature
      ↓
Strategy Compatibility
      ↓
Best Matching Variant
```

---

# 我建议 V1 的 Strategy Routing 是四级 fallback

```Plain Text
① 精确 Variant
      ↓ 找不到

② 相似 Variant
      ↓ 不适合

③ Parent Strategy + 临时 Delta
      ↓ Parent 都不匹配

④ 从 Role Pool 创建新临时 Strategy
```

例如：

```Plain Text
用户第一次：
分析火山灾难新闻

没有 DisasterReport
```

系统可能：

```Plain Text
BaseReport
+
Web Research
+
Freshness Check
+
Timeline Verifier
```

先完成任务。

如果这种需求重复：

```Plain Text
↓
DisasterReport Variant
```

这就很符合“组织经验积累”。

---

# 那什么时候把子分支能力提升回 Parent？

这个比“merge”更重要。

比如 Academic 分支演化出：

```Plain Text
source_reliability_verification
```

我们后来发现：

```Plain Text
Academic +8%
News     +5%
Disaster +7%
General  +4%
```

也就是说，这个东西根本不是 Academic 专属。

那么：

```Plain Text
Academic Delta
        ↓
Cross-Variant Validation
        ↓
Promote to Parent
```

变成：

```Plain Text
BaseReportStrategy v5
+
Source Reliability Check
```

所有子 Strategy 自动受益。

所以最终其实有两个方向：

```Plain Text
向下：
Specialization
父 → 子

向上：
Generalization
子 → 父
```

这甚至可以成为一个不错的研究点。

---

# V1 要不要做兄弟 Strategy 合并？

我建议：

# 暂时不做。

比如：

```Plain Text
NewsReport
DisasterReport
```

后来越来越相似。

理论上可以：

```Plain Text
merge
```

但第一版不值得增加这个复杂度。

先允许：

```Plain Text
Child → Parent Generalization
```

已经足够。

所以第一版 Strategy Tree：

```Plain Text
                 Report Base
                  /       \
                 /         \
          Academic         News
                              \
                            Disaster?
```

不要做 DAG 式复杂 merge。

---

# Strategy Freeze 机制

你之前说：

> 性能提升不够就锁定。

这个完全应该保留。

例如：

```Plain Text
过去连续 3 次 Evolution

v4 → v5 +0.6%
v5 → v6 +0.4%
v6 → v7 rejected
```

则：

```Plain Text
Report.Academic
status = FROZEN
```

直到出现：

```Plain Text
新的失败模式
任务分布明显变化
新 Tool 出现
用户明确要求重新优化
```

再：

```Plain Text
UNFREEZE
```

这样才能回答老师：

> “你的系统会不会永远烧 Token 自我进化？”

不会。

# 二、Failure Attribution：失败到底怪谁？

我现在越来越认为：

> **这是 EvoTeam 最有技术含量的部分之一。**

因为如果归因错了，后面所有 Evolution 都是错的。

假设最后报告数字错了。

可能有：

```Plain Text
Planner
 ↓
Analyst
 ↓
Writer
 ↓
Verifier
```

问题可能是：

```Plain Text
Analyst 算错
```

但也可能：

```Plain Text
Planner 没要求数值验证
```

甚至：

```Plain Text
Analyst 算错
+
Verifier 没发现
```

所以不能只找：

> 一个“罪魁祸首”。

---

# 我建议 Failure Attribution 支持多因归因

例如：

```JSON
{
  "failure": "numeric_error",

  "causes": [
    {
      "type": "origin",
      "target": "analyst",
      "confidence": 0.92
    },
    {
      "type": "control_failure",
      "target": "verifier",
      "confidence": 0.81
    }
  ]
}
```

这里我特别建议区分两个概念：

### Origin Failure

谁产生了错误？

例如：

```Plain Text
Analyst
```

### Detection / Control Failure

为什么错误没有被阻止？

例如：

```Plain Text
Verifier
```

这个会比：

> “Analyst 有问题。”

深入很多。

---

# Attribution 不应该只靠一个 LLM Agent

如果我们设计：

```Plain Text
Run Failed
 ↓
AttributionAgent：
“我觉得 Analyst 有问题”
```

这个非常容易被评委攻击：

> “那如果 Attribution Agent 自己判断错了呢？”

所以我建议：

# Evidence-Based Attribution

三层证据。

```Plain Text
Deterministic Evidence
        +
Trace Evidence
        +
LLM Reasoning
```

---

## 第一层：确定性证据

例如：

```Plain Text
Python Tool:
exit_code = 1
```

那 Tool Failure 几乎不用 LLM 猜。

或者：

```Plain Text
用户约束：
budget <= 10000

Result:
budget = 15000
```

ConstraintChecker 可以确定：

```Plain Text
constraint_violation
```

---

## 第二层：Trace Provenance

我们追踪数据到底从哪来的。

例如最后：

```Plain Text
Writer 输出：
增长率 = 31%
```

Trace 能发现：

```Plain Text
Writer 引用了 Analyst output #A17
```

而：

```Plain Text
Analyst #A17
growth_rate = 31%
```

真实应该：

```Plain Text
13%
```

那么错误 provenance 已经指向 Analyst。

---

## 第三层：LLM Attribution

只有当前两层无法直接判断时：

```Plain Text
Attribution Agent
```

读取**压缩后的证据**：

```Plain Text
Task
Failure
Relevant Trace Slice
Agent Output
Tool Output
Evaluator Evidence
```

再判断：

```JSON
{
  "primary_target": "planner",
  "target_type": "role",
  "reason": "verification step was omitted",
  "confidence": 0.74
}
```

---

# Attribution 最有意思的一步：Counterfactual Replay

这个是我非常建议后续做的，而且很适合答辩。

如果系统怀疑：

> Analyst Prompt 有问题。

那可以做一个小实验：

```Plain Text
原 Strategy
Planner → Analyst-v1 → Verifier
```

只换：

```Plain Text
Analyst-v2
```

其他全部保持一样。

然后重新跑几个失败类型相近的任务。

如果：

```Plain Text
numeric_error
从 35%
降到 8%
```

那么：

> Analyst Attribution 得到进一步证据支持。

这其实接近一种：

# Counterfactual Attribution

也就是：

> 如果我只改变这个因素，错误是否明显减少？

这比让 LLM 一拍脑袋说“是 Analyst 的锅”强非常多。

---

# Attribution 应该输出“修改建议层级”

例如最终输出：

```JSON
{
  "failure_tag": "missing_citation",

  "attributions": [
    {
      "target_type": "prompt",
      "target": "writer",
      "confidence": 0.72
    },
    {
      "target_type": "topology",
      "target": "writer->final",
      "confidence": 0.84
    }
  ],

  "recommended_scope": "team_structure"
}
```

这里意味着：

> 单改 Writer Prompt 可能不够，真正缺的是一个 CitationVerifier。

于是后面的 Mutation Engine 才知道：

```Plain Text
不要只产生 Prompt Mutation
还应该产生 Topology Mutation
```

---

# Attribution 的置信度很重要

如果：

```Plain Text
confidence > 0.8
```

可以自动进入 Evolution。

如果：

```Plain Text
0.5 < confidence < 0.8
```

多生成几个 Candidate 做实验。

如果：

```Plain Text
confidence < 0.5
```

不要贸然进化。

标记：

```Plain Text
NEEDS_MORE_EVIDENCE
```

继续收集 Run。

这也对应：

> **好的自演进系统必须知道什么时候“不知道”。**

# 三、Mutation Search：到底怎么寻找下一代 Strategy？

这个问题我现在反而觉得第一版应该**故意做简单但严谨**。

千万不要一上来：

```Plain Text
Genetic Algorithm
MCTS
RL
Population Search
```

那项目会迅速变成搜索算法比赛。

---

# V1 Mutation Search 的基本原则

我建议：

> **一次 Candidate 尽量只改一个核心因素。**

比如不要：

```Plain Text
Candidate v4

+ 改 Analyst Prompt
+ 加 Verifier
+ 改 Tool
+ 改 Planner
+ 并行执行
```

即使最后提升了：

> 你也不知道是谁造成的。

所以第一版要强调：

# Minimal Mutation

例如：

```Plain Text
Candidate A
只改 Analyst Prompt

Candidate B
只增加 Verifier

Candidate C
只强制 Python Tool
```

然后比赛。

这极其利于：

- 可解释；
- 消融；
- Attribution；
- PPT；
- Debug。

---

# 一个 Evolution Event 最多生成几个 Candidate？

我推荐：

# 2～3 个。

假设：

```Plain Text
numeric_error
```

Attribution：

```Plain Text
Analyst 0.87
Missing Verification 0.75
```

Evolution Planner 可以生成：

```Plain Text
Candidate A
Prompt Mutation
────────────────
Analyst 增加计算检查要求
```

```Plain Text
Candidate B
Tool Mutation
─────────────
复杂计算强制 Python
```

```Plain Text
Candidate C
Topology Mutation
─────────────────
增加 Verifier
```

然后分别验证。

这比：

> LLM 生成一个“自认为最优”的方案

稳定得多。

---

# Candidate Search 应该是分层漏斗

不要每个 Candidate 上来就跑整个 Validation Set。

成本太高。

设计成：

```Plain Text
Mutation Proposal
      ↓
Static Validation
      ↓
Smoke Test
      ↓
Mini Validation
      ↓
Full Validation
      ↓
Promotion
```

---

## Stage 1：Static Validation

检查：

```Plain Text
Graph 是否合法？
Role 是否存在？
Tool 是否存在？
是否有无限循环？
Prompt 是否为空？
```

这一步不调用 LLM。

---

## Stage 2：Smoke Test

跑：

```Plain Text
2~3 个任务
```

如果直接崩：

```Plain Text
Reject
```

---

## Stage 3：Mini Validation

跑：

```Plain Text
5~10 个代表任务
```

快速筛选：

```Plain Text
3 Candidate
 ↓
留下 1~2 个
```

---

## Stage 4：Full Validation

最终候选再跑：

```Plain Text
完整 Validation Set
```

与 Current Strategy 正面对比。

这样节省非常多 Token。

---

# Candidate 不是一定要比质量更高

这是一个很重要的思想。

可能有两类演进。

## Quality Evolution

例如：

```Plain Text
Quality +7%
Cost +8%
```

合理。

---

## Efficiency Evolution

例如：

```Plain Text
Quality -0.3%
Cost -30%
Latency -25%
```

这其实也可能值得 Promote。

所以应该允许两种 Promotion Mode。

---

### Quality-oriented Promotion

例如：

```Plain Text
Quality +≥3%
Success Rate 不下降
Cost +≤20%
Latency +≤25%
```

---

### Efficiency-oriented Promotion

例如：

```Plain Text
Quality 下降 ≤1%
Cost ↓≥15%

OR

Latency ↓≥20%
```

这特别适合：

# Agent Pruning。

比如：

```Plain Text
去掉 Critic
```

结果：

```Plain Text
Quality:
87.4 → 87.0

Cost:
1.00 → 0.71

Latency:
1.00 → 0.68
```

那可能应该：

```Plain Text
Promote
```

---

# Mutation Operator 最好是 Typed Operator

不要让 LLM 输出：

> “请优化这个系统。”

而让它选择：

```Plain Text
MutationType
```

例如：

```Plain Text
PROMPT_UPDATE
SKILL_ADD
SKILL_REMOVE
TOOL_ADD
TOOL_REMOVE

ROLE_ADD
ROLE_REMOVE

EDGE_ADD
EDGE_REMOVE

MAKE_PARALLEL
MAKE_SEQUENTIAL

ADD_CONDITION
CHANGE_RETRY_POLICY
CHANGE_REPLAN_POLICY
```

然后给参数。

例如：

```JSON
{
  "type": "ROLE_ADD",
  "role": "verifier",
  "after": "analyst",
  "condition": "numeric_complexity > medium"
}
```

这就是：

# Schema-Constrained Mutation

而不是自由代码生成。

我非常推荐这个。

# 七、我认为此时 EvoTeam 已经出现了一个很清楚的核心公式

以后 PPT 甚至可以画成：

```Plain Text
                 Experience
                     │
                     ▼
Task ─────────→ Strategy ─────────→ Run
                  │                   │
                  │                   ▼
                  │               Evaluation
                  │                   │
                  │                   ▼
                  │              Attribution
                  │                   │
                  │                   ▼
                  │               Mutation
                  │                   │
                  │                   ▼
                  └──────────── Validation
                                      │
                             ┌────────┴────────┐
                             ▼                 ▼
                          Promote            Reject
                             │
                             ▼
                      Next Generation
```

而最核心的三句话已经可以变成：

> **任务决定初始组织。**
> 
> **证据决定问题归因。**
> 
> **验证决定组织是否换代。**

我觉得这三句话甚至比“Prompt Evolution / Tool Evolution / Team Evolution”更加适合作为 EvoTeam 的核心设计哲学。

下一轮最值得做的事情已经不是继续发散机制，而是把这三个设计正式更新进 `PRODUCT_SPEC_V1`、`ARCHITECTURE`、`EXPERIMENTS` 和 `DECISIONS`，然后开始把 **PPT 的故事线和架构图**冻结下来。
