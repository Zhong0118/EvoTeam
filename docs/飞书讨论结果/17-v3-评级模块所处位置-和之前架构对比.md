## Candidate 到底是什么？

Candidate 就是：

> **“根据当前 Strategy 修改出来、但还没有资格正式上线的新 Strategy 候选版本。”**

例如当前：

```Plain Text
Current Strategy v0

Planner
   ↓
Executor
   ↓
Critic
```

最近 10 个任务反复资源冲突，Monitor 触发演进：

```Plain Text
Experience
   ↓
Failure Attribution
   ↓
发现：
Executor 经常制造资源冲突
Critic 又经常没检查出来
```

EvolutionManager 开始组织一次演进：

```Plain Text
Current Strategy v0
        ↓
Mutation Proposal
        ↓
ADD Verifier
        ↓
Candidate Strategy v1
```

于是出现：

```Plain Text
Candidate Strategy v1

Planner
   ↓
Executor
   ↓
Verifier
   ↓
Critic
```

它现在只是一个**候选方案**。

不能直接：

```Plain Text
v1 → 给真实用户使用
```

而是：

```Plain Text
Current v0
     vs
Candidate v1
     ↓
Validator
     ↓
Validation Set 上做实验
```

如果证明：

```Plain Text
质量 ↑
错误率 ↓
成本增加可接受
```

才：

```Plain Text
Candidate v1
   ↓ Promote
Current v1
```

否则：

```Plain Text
Candidate v1
   ↓
REJECTED
```

所以你说：

> “是不是 EvolutionManager 处理后才出现，用来做比较？”

**基本正确。**

更精确一点：

```Plain Text
EvolutionManager 启动演进流程
        ↓
Attribution
        ↓
Mutation / Candidate Generator
        ↓
Candidate Strategy 出现
        ↓
Validator 拿它和 Current 比
```

也就是说，**Candidate 本身仍然是 Strategy**，不是一个新的对象种类。

代码上甚至可以只是：

```Python
Strategy(
    version=1,
    parent_version=0,
    status="candidate",
    ...
)
```

和 Current Strategy 使用完全相同的数据结构，只是生命周期状态不同。

# 最重要的是：六层不是六个“运行阶段”

这一点要分清。

它首先是：

> **概念和职责层级。**

真正“时间上怎么跑”，是另一条轴。

整个系统在时间上其实只有两个大时期：

```Plain Text
ONLINE
在线执行

OFFLINE
离线演进
```

# 一次普通任务的时间顺序

绝大多数时间系统都处于这一条：

```Plain Text
① Task
   ↓
TaskProfile

② 查询基础能力配置

③ 找到 Current Strategy

④ Orchestrator 开始执行
   ↓
创建 Team
   ↓
创建 AgentInstance
   ↓
Planner / Executor / Critic...
   ↓
Run 完成

⑤ Evaluator 打分
   ↓
Trace + Metrics
   ↓
SealedRun
   ↓
Experience 保存
   ↓
StrategyMonitor 更新长期统计
```

到这里，一次任务结束。

**通常不会进入第 ⑥ 层。**

这点很重要。

正常情况下：

```Plain Text
第 1~5 层
```

天天运行。

而：

```Plain Text
第 6 层
```

偶尔运行。

# 什么情况下进入第 ⑥ 层？

StrategyMonitor 检查：

```Plain Text
最近 10 个 Run
```

发现：

```Plain Text
resource_conflict = 4 次

或者：

quality ↓ 8%

或者：

Critic 贡献很低但 cost 很高
```

达到人为设定 + baseline 校准后的 Trigger：

```Plain Text
StrategyMonitor
      ↓
EvolutionTrigger = TRUE
```

然后才：

```Plain Text
第 ⑥ 层启动
```

# Candidate 可以有不止一个

比如 Failure Attribution 得到：

> Executor 资源冲突 + Critic 漏检。

EvolutionManager 可能允许 Candidate Generator 生成三个方案：

```Plain Text
Current v0
│
├── Candidate A
│   └── 改 Executor Prompt
│
├── Candidate B
│   └── Executor 强制调用 constraint_checker
│
└── Candidate C
    └── ADD Verifier
```

然后：

```Plain Text
Validator
```

做：

```Plain Text
Current
vs A
vs B
vs C
```

最终可能发现：

```Plain Text
             Quality   Error    Token

Current       80        20%       1.00
A             83        15%       1.01
B             89         4%       1.05
C             90         3%       1.25
```

于是虽然 C 质量最高：

```Plain Text
C 太贵
```

最后可能选择：

```Plain Text
Candidate B
```

Promote：

```Plain Text
B → Current v1
```

所以：

> **Candidate 就是“演进搜索空间里值得拿去考试的几个新 Strategy 方案”。**

# 那 Candidate 属于第 ③ 层还是第 ⑥ 层？

这是一个很好的概念问题。

从**数据类型**来说：

```Plain Text
Candidate Strategy
```

当然还是：

```Plain Text
Strategy
```

所以其结构属于：

> **③ 核心组织策略层。**

但是它产生、验证和晋级的生命周期行为发生在：

> **⑥ 演进治理层。**

可以理解：

```Plain Text
③ 定义“Strategy 是什么”

⑥ 管理“Strategy 怎么从 Current 变成 Candidate，再变成 Current”
```

这一点以后写代码也一样。

比如：

```Python
# domain/strategy.py

class Strategy(BaseModel):
    ...
```

而：

```Python
# evolution/manager.py

candidate = mutation_engine.mutate(current)
```

Candidate 不需要：

```Python
class CandidateStrategy(Strategy):
    ...
```

除非后面真有特殊需求。

完全可以只是：

```Python
candidate.status = StrategyStatus.CANDIDATE
```

# 你现在最好把两个“闭环”分开记

## 闭环 A：Task Execution Loop

天天运行：

```Plain Text
Task
↓
Current Strategy
↓
Orchestrator
↓
Team
↓
AgentInstance
↓
Critic / Verifier
↓
Run
↓
Evaluator
↓
Experience
```

目的：

> **把当前任务做好，同时留下证据。**

---

## 闭环 B：Strategy Evolution Loop

偶尔运行：

```Plain Text
Experience
↓
Monitor
↓
Trigger
↓
EvolutionManager
↓
Attribution
↓
Mutation
↓
Candidate
↓
Validator
↓
Promote / Reject
```

目的：

> **改变未来任务默认使用的组织方式。**

这样就非常清楚了。

# 最后我建议对你原来六层做 4 个正式修订

原版不是废掉，而是升级：

1. **② 增加 `AgentConfig`**
2. 因为 Role / Prompt / Skill / Tool 最终必须先组合成一个可执行 Agent 定义。
3. **④ 明确加入 `Orchestrator`**
4. Team 不会自己跑，Orchestrator 是在线执行控制器。
5. **⑤ 拆清 `Evaluator / Experience / StrategyMonitor`**
6. 一个给单 Run 打分，一个存历史，一个看长期趋势。
7. **⑥ 加 `EvolutionManager + Validator`，并把 Failure Attribution 改成 Outcome Attribution**
8. Candidate 就诞生在这里。

所以回答你最后一句：

> **“现在还适配吗？”**

答案是：

> **非常适配，而且我建议继续坚持六层；只是现在我们已经能把每一层的对象、职责和运行时机填完整了。**

到这一版以后，六层负责回答：

> **“东西放在哪里？”**

而两个闭环负责回答：

> **“东西什么时候工作？”**

这两个视角叠起来，我认为就是目前最清楚的一版 EvoTeam 心智模型。
