> **EvoTeam 到底是什么？它真正创新的对象是什么？为什么评委应该相信这是“自演进”，而不是几个 Agent + 自动改 Prompt？**

# 一、我认为我们现在其实有 3 条产品路线

## 路线 A：通用自演进 Agent 平台

定位：

> 用户输入任意复杂任务，EvoTeam 自动组建 Agent Team、执行、评价并持续演进。

类似：

```Plain Text
                 EvoTeam Platform
                       │
             输入任意复杂任务
                       │
              自动理解任务类型
                       │
              自动组建 Agent Team
                       │
                   执行任务
                       │
                自我评价和演进
```

听起来最大气。

### 优点

非常贴题：

- 多 Agent
- 动态分工
- 自演进
- 通用平台

PPT 也很好讲。

### 但我会直接攻击它

评委一句话：

> “你们凭什么说任意复杂任务都能动态组队？”

我们很难证明。

三个人、比赛周期有限，不可能覆盖：

```Plain Text
代码
科研
数据
商业
规划
办公
金融
...
```

最后很可能变成：

> 通用只是 PPT 上通用。

所以：

**不建议把“通用 Agent 平台”作为产品核心承诺。**

# 二、路线 B：做一个具体业务 Agent 产品

例如：

> 自演进科研助手

或者：

> 自演进数据分析系统

那么我们可以把 Agent 做得非常深入。

例如数据分析：

```Plain Text
Data Planner
Data Cleaner
Python Analyst
Insight Agent
Verifier

```

并不断演进。

### 优点

容易做深。

实验也容易：

```Plain Text
准确率
计算错误
SQL
Python
图表
```

很具体。

### 但有一个很大的问题

赛题给出的：

> 报告生成 / 数据分析 / 任务规划

明显希望看到一种**通用的 Multi-Agent Evolution 思想**。

如果我们只做：

> 销售数据分析助手

评委可能问：

> 这到底是“自演进多智能体系统”，还是一个数据分析应用？

这样会把真正有意思的“组织演进”弱化掉。

所以：

**不建议把产品锁死在某一个业务场景。**

# 六、我们必须把“演进对象”定义死

这是我认为目前整个方案最关键的一个思想。

不要说：

> Agent 在演进。

因为太模糊了。

也不要说：

> Prompt 在演进。

因为太小了。

我们真正应该定义一个东西：

# Strategy

也就是：

> **Team Strategy = 一支 Agent Team 完成某一类任务的方法。**

它包含：

```Plain Text
Strategy
│
├── Team Structure
│   ├── Agent 类型
│   ├── Agent 数量
│   └── 协作 Graph
│
├── Prompt Policy
│
├── Tool Policy
│
├── Routing Policy
│
└── Execution Policy
```

例如：

```Plain Text
DataAnalysisStrategy v1

Agents:
Planner
Analyst
Critic

Tools:
Python optional

Routing:
Planner → Analyst → Critic
```

经过演进：

```Plain Text
DataAnalysisStrategy v2

Agents:
Planner
Analyst
CodeVerifier
Critic

Tools:
numeric task → Python mandatory

Routing:
Planner
  ↓
Analyst
  ↓
CodeVerifier
  ↓
Critic
```

所以以后我们不是说：

> Agent 进化了。

而是：

> **Strategy 从 v1 演进到 v2。**

这个会让整个项目突然变得非常清晰。

---

# 七、自演进的正式定义，我建议直接这么定

以后 PPT、论文、答辩都可以围绕它。

> **EvoTeam 将自演进定义为：系统基于跨任务历史执行数据和评价结果，自动生成可版本化的 Strategy 变更，并在独立验证任务上完成效果验证，只有表现优于当前 Strategy 的候选方案才会被晋升并影响未来任务。**

拆开就是：

```Plain Text
Historical Experience
        ↓
Failure Pattern
        ↓
Evolution Proposal
        ↓
Candidate Strategy
        ↓
Validation
        ↓
Promote / Rollback
        ↓
Future Tasks
```

这一个定义，可以挡住很多攻击。

我们直接：

```Plain Text
EvoTeam Evolution
─────────────────

持续

```

这就是非常强的故事。

# 二十六、但现在还有 5 个问题，我认为我们下一轮必须继续狠狠干

这五个一旦解决，基本就可以开始做 PPT 正稿了。

### 问题 1

**动态组队是“第一次任务就动态”，还是“先选择已有 Strategy，再通过历史演进”？**

这是两个完全不同的产品哲学。

---

### 问题 2

**Evolution Engine 到底由谁产生 Mutation？**

```Plain Text
LLM?
规则?
LLM + Rule?
搜索算法?
```

---

### 问题 3

**Strategy 是按任务类型维护，还是全局只有一套？**

例如：

```Plain Text
ReportStrategy v4
DataStrategy v7
PlanningStrategy v3
```

还是：

```Plain Text
Global EvoTeam Strategy v10
```

我目前明显倾向前者。

---

### 问题 4

**“历史经验”到底存什么？**

不能只是：

```Plain Text
过去的聊天记录
```

应该定义：

```Plain Text
Failure
Cause
Context
Team
Action
Outcome
```

这决定后面 Memory 设计。

---

### 问题 5

**Team Evolution 到底允许多大胆？**

例如只允许：

```Plain Text
Add / Remove Role
Change Prompt
Change Tool
```

还是连：

```Plain Text
创建新角色
修改图
并行执行
条件执行
```

都允许。

第一版不能太自由，否则 Validation 成本会爆炸。

---

我建议我们下一轮就围绕这 5 个问题继续碰撞，而且这次可以更狠一点：**每个问题我先给 2～3 个方案，然后站在评委、工程负责人、研究者三个视角分别攻击，最后把 EvoTeam V1 产品定义彻底冻结。**

等这五个问题拍板，我们就已经足够开始做第一版正式 PPT，而不是概念草图。
