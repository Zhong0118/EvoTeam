## 我认为目前最严重的问题：Roadmap 和核心创新不一致

这一点我想单独强调。

现在你们实际上有两条叙事：

**叙事 A：**

```Plain Text
Prompt Evolution
→ Tool Evolution
→ Team Evolution
```

这是当前 Architecture / Roadmap 的工程渐进路径。

但你们最有价值的产品叙事其实是：

```Plain Text
历史任务
   ↓
失败模式
   ↓
组织归因
   ↓
Strategy Mutation
   ↓
Candidate Team
   ↓
Validation
   ↓
Promote / Rollback
```

然后出现：

```Plain Text
Planner → Executor → Critic
                 ↓
Planner → Executor → Verifier → Critic
```

后者才真正是 **EvoTeam**。

如果做到比赛中期，你们只能展示：

> “我们发现 Executor 经常犯错，所以让 LLM 自动改了 Executor Prompt。”

我会直接给这个项目一个非常危险的评价：

> **这是一个不错的 Self-Improving Agent，但还不是一个有说服力的 Self-Evolving Agent Team。**

尤其你们自己的 Related Work 已经把 Reflexion、Voyager、JiuwenSwarm、Meta-Team、EvoMAS、GPTSwarm 都列出来了，这意味着你们不能假装“自动改 Prompt / Skill”本身还有多强的差异化。

## 所以我现在反而建议把“核心创新点”进一步收缩成三个

你们之前列出来的很多能力都可以保留，但**真正拿出去讲的只有三个**：

**① Strategy as Evolvable Organization**

不是 Agent 在进化，而是：

```Plain Text
Strategy =
Roles
+ Skills
+ Tools
+ Topology
+ Execution Policy
```

而且 Strategy 有：

```Plain Text
Version
Parent
Candidate
Generation
Status
```

这其实是你们整个系统最重要的数据抽象。

**② Evidence-driven Bounded Mutation**

不是：

```Plain Text
失败
→ LLM 随便想个改法
```

而是：

```Plain Text
Trace
+ Evaluation
+ Failure Pattern
      ↓
Attribution Evidence
      ↓
受 Schema 限制的 Mutation
```

允许：

```Plain Text
ADD
REMOVE
REPLACE
REWIRE
CONDITIONALIZE
```

禁止无限创造 Role、无限 Graph、自由生成任意 Workflow。这一点现在文档方向是对的。

**③ Evolution Governance**

这个我现在反而越来越喜欢。

不是只回答：

> 系统会不会自己改？

而是回答：

> **系统凭什么改？改了什么？新方案真的更好吗？该不该上线？坏了能不能退回去？**

也就是：

```Plain Text
Proposal
   ↓
Candidate
   ↓
Validation
   ↓
Promote / Reject
   ↓
Version History
   ↓
Rollback
```

这既是技术点，也是你们非常容易做成可视化产品价值的地方。Related Work 最后其实也已经自然推到了这个概念。

## 我会暂时降级的东西

`Strategy Family / Branch / Parent Promotion` 很有意思，但我现在会把它从“核心创新”降成 **V1.5 / 论文扩展项**。

不是因为它不好，而是因为它一下带来了：

```Plain Text
Task Distribution Detection
Inheritance
Specialization
Generalization
Branch Threshold
Parent Promotion
Strategy Explosion
```

一整个新的研究问题。

你们现在甚至还没证明：

```Plain Text
Strategy v0
   ↓
根据跨任务经验
   ↓
Strategy v1
   ↓
held-out tasks 上真的更好
```

此时就开始讨论：

```Plain Text
AcademicStrategy
NewsStrategy
GeneralStrategy
子分支
父分支
泛化
合并
```

太容易进入“架构很好看，但实验做不出来”的状态。

所以我的建议会变成：

> **先证明 Evolution，再证明 Specialization；先证明单条 Strategy lineage，再做 Strategy Family。**

## 如果现在让我替你们冻结一句项目定义

我目前会定成：

> **EvoTeam 是一个基于 openJiuwen 的经验驱动多智能体组织演进系统，通过跨任务执行证据对 Team Strategy 进行受约束的结构变异，并通过独立验证、晋升与回滚机制实现可验证、可治理的持续演进。**

这句话比：

> “让 Agent Team 像真实组织一样不断成长”

少一点浪漫，但**技术边界清楚得多，而且很难被一句“这不就是改 Prompt 吗？”打掉。**
