# 二、Strategy 到底是什么？

你问：

> Strategy 是不是包含了所有 Workflow、各种调度？还有什么？

准确说：

> **Strategy = 一支 Agent Team 应该如何组织、配置和协作的完整“可执行组织方案”。**

可以把它理解成：

```Plain Text
Strategy
=
Who
+
Capability
+
Structure
+
How
```

具体：

```Plain Text
Who
= 哪些 Agent / Role 参与

Capability
= 每个 Agent 用什么 Prompt / Skill / Tool

Structure
= Agent 之间怎么连接

How
= 顺序、并行、条件、重试、Replan、Routing 等
```

所以它确实涵盖 Workflow / 调度的**规则和结构**。

但这里有一个非常重要的细节：

## Strategy ≠ Workflow

例如 Strategy v3 规定：

```Plain Text
如果任务需要数值计算：
    Planner
      ↓
    Analyst
      ↓
    Verifier

如果任务很简单：
    Planner
      ↓
    Analyst
```

这是 **Strategy**。

具体来了一个任务：

> 分析某数据表并计算增长率

系统根据 Strategy v3 最终生成：

```Plain Text
Planner → Analyst → Verifier
```

这一次实际执行出来的路径，才叫：

> **Execution Plan / Workflow**

所以：

```Plain Text
Strategy
   ↓ 根据 Task 实例化
Workflow / Execution Plan
```

这个区别非常重要。

# 三、Role 是什么？

你理解得基本正确：

> **Role 是提前定义好的职责原型。**

例如：

```Plain Text
Planner
Researcher
Analyst
Writer
Verifier
Critic
```

Role 回答的问题是：

> **“你在团队里负责什么？”**

例如：

```Plain Text
Planner
= 分析问题、拆任务、制定计划

Verifier
= 检查事实、数字、约束是否正确
```

V1 我强烈建议：

> **Role Pool 基本固定，不让系统随便创造 Role。**

因此：

```Plain Text
Role Pool
├── Planner
├── Researcher
├── Analyst
├── Writer
├── Verifier
└── Critic
```

Strategy 可以：

```Plain Text
选择 Role
删除 Role
增加已有 Role
调整 Role 的能力配置
```

但先不要：

```Plain Text
LLM：我今天创造一个
SuperHyperMetaPlanningAgent
```

否则演进空间直接爆炸。

---

# 四、Role 和 Agent 到底有什么区别？

这是你现在最纠结的地方之一。

不要把：

```Plain Text
Role = Agent
```

完全画等号。

最好这样理解：

> **Role 是“职位”。Agent 是“占据这个职位、真正工作的执行实体”。**

类比公司：

```Plain Text
Role = 软件工程师
Agent = 张三

Role = 产品经理
Agent = 李四
```

在 EvoTeam 中：

```Plain Text
Role
    ↓ 配置
Agent Spec
    ↓ 运行时创建
Agent Instance
```

例如：

```Plain Text
Role:
Verifier
```

Strategy 对这个 Role 配置：

```Plain Text
Prompt:
"你负责检查数字..."

Skills:
- numeric-verification

Tools:
- Python

Model:
xxx
```

这整个配置可以叫：

> **AgentSpec**

然后真正运行任务时，通过 openJiuwen 创建一个：

> **AgentInstance**

所以完整关系是：

```Plain Text
Role
= 职责模板
        ↓
AgentSpec
= Strategy 中配置好的一个 Agent 节点
        ↓
AgentInstance
= 当前 Run 真正运行的 Agent
```

# 六、Prompt 在哪里？

对：

> **Prompt 是 Strategy 的一部分。**

但更准确地讲：

Strategy 不一定物理保存 Prompt 全文，而可能保存：

```Plain Text
prompt_id = verifier_prompt_v3
```

也就是说：

```Plain Text
Prompt Registry
     ↑
 Strategy 引用
```

这对 Skill / Tool 也是一样。

这个设计会清晰很多。

不要：

```Plain Text
Strategy
里面塞一整个 Python Tool 实现
里面塞一整个 Skill 文件
里面塞所有 Prompt 源代码
```

应该是：

```Plain Text
Strategy
├── prompt_ref
├── skill_ref
└── tool_ref
```

因此 Strategy 是：

> **配置和组合这些能力。**

而不是：

> 所有底层能力实现本身。

---

# 七、Skill 呢？

同理。

Skill 回答：

> **“这个 Agent 会什么可复用的方法 / 能力？”**

比如：

```Plain Text
Researcher
├── Skill: web_research
├── Skill: source_ranking
└── Tool: Search
```

Strategy 决定：

```Plain Text
给 Researcher 配哪些 Skill
```

Evolution 也可以调整：

```Plain Text
Strategy v2:
Researcher.skills = [web_research]

Strategy v3:
Researcher.skills =
[
  web_research,
  source_reliability_check
]
```

所以：

> **不是 Skill 属于 Strategy 本体的底层实现，而是 Skill Assignment 属于 Strategy。**

这个措辞以后很重要。

---

# 八、Tool 也是一样

Tool 本身：

```Plain Text
Python
Browser
Search
Database
```

是系统已有的外部能力。

Strategy 管的是：

```Plain Text
谁可以用哪个 Tool？
什么时候允许调用？
优先用哪个？
是否必须调用？
失败怎么办？
```

例如：

```Plain Text
Analyst:
  tools:
    - Python

tool_policy:
  numeric_calculation:
    require_python = true
```

所以 Strategy 演进可能发生：

```Plain Text
Before:
Analyst 没有 Python

After:
Analyst → Python enabled
```

或者：

```Plain Text
Before:
LLM 自己算

After:
数值问题强制 Python
```

这就是 Tool Policy Mutation。

# 九、Team 到底是什么？

这个也必须重新定义。

**Team 不是“几个 Role 的集合”这么简单。**

Team 是：

> **针对某一个具体 Task，根据某一个 Strategy，实际组建出来的一组 Agent。**

例如 Task：

```Plain Text
分析一份销售数据
```

Task Analyzer 得到：

```Plain Text
needs_calculation = true
needs_writing = true
needs_search = false
```

当前 Strategy 根据这些条件决定：

```Plain Text
Team
├── Planner Agent
├── Analyst Agent
├── Writer Agent
└── Verifier Agent
```

所以：

```Plain Text
Task
 ↓
Task Profile
 ↓
Strategy
 ↓
Team
```

你的这句话：

> “Task 催生 Team？”

非常接近。

更准确：

> **Task 提供需求，Strategy 决定如何根据这个需求组建 Team。**

# 十、因此 Task、Strategy、Team 三者关系是最核心的一条链

记住这个就行：

```Plain Text
                 Strategy
                /        \
               /          \
              ↓            ↓
Task → Task Profile → Resolve
                        ↓
                      Team
                        ↓
                   Workflow
                        ↓
                       Run
```

或者一句话：

> **Task 说“我要做什么”；Strategy 说“应该组织谁、怎么做”；Team 是“这次真正派谁上场”；Workflow 是“这次具体怎么走”；Run 是“真正执行了一遍”。**

# 十一、你可以用“公司”类比整个系统

这个类比非常适合 EvoTeam。

```Plain Text
Task
=
公司接到一个项目


Role
=
职位类型

Planner / Analyst / Verifier


Skill
=
员工掌握的方法论

数据分析、搜索、引用检查


Tool
=
员工可使用的工具

Python、Search、Database


Prompt
=
岗位工作说明 + 当前工作指令


Strategy
=
公司针对这类项目的组织方案

派哪些岗位？
每个岗位配什么能力？
谁先做？
谁审核？
谁能找谁？
什么时候返工？


Team
=
针对今天这个项目实际派出的项目组


Agent
=
项目组里真正工作的成员


Workflow
=
这次项目实际执行流程

=
```

其实 EvoTeam 最核心的思想就是：

> **不是让某个“员工”自己越来越聪明，而是让“组织做事的方法”越来越好。**

这句话非常接近你们最终项目灵魂。

# 十二、这样一来，“演进”到底改哪里也清晰了

Evolution **主要修改 Strategy**。

```Plain Text
Strategy v1
│
├── Planner
├── Analyst
├── Critic
└── Planner → Analyst → Critic
```

运行了 20 个任务以后发现：

```Plain Text
numeric_error 高
```

于是：

```Plain Text
Mutation:
ADD Verifier
```

产生：

```Plain Text
Strategy v2 Candidate
│
├── Planner
├── Analyst
├── Verifier
├── Critic
└── Planner → Analyst → Verifier → Critic
```

Validation 后发现：

```Plain Text
Accuracy ↑
Cost +5%
Latency +8%

acceptable
```

于是：

```Plain Text
v2 → ACTIVE
v1 → RETIRED
```

之后又发现：

```Plain Text
Critic
Quality Gain ≈ 0
Cost ↑
```

于是：

```Plain Text
Mutation:
REMOVE Critic
```

得到：

```Plain Text
Strategy v3
Planner → Analyst → Verifier
```

这时候整个项目故事就非常干净。

# 十三、Strategy 本身最好再拆成“内容”和“治理信息”

你之前说：

> Strategy 还要有版本、状态、效果。

没错。

但是为了架构干净，我建议概念上拆成两部分：

```Plain Text
Strategy
│
├── Strategy Definition
│   │
│   ├── Agent Specs
│   ├── Prompt Assignment
│   ├── Skill Assignment
│   ├── Tool Assignment
│   ├── Topology
│   └── Orchestration Policy
│
└── Strategy Metadata
    │
    ├── id
    ├── version
    ├── generation
    ├── parent
    ├── status
    ├── created_reason
    └── metrics
```

也就是说：

### Definition

回答：

> **“这个策略具体怎么工作？”**

### Metadata

回答：

> **“这个策略是谁、从哪来、表现如何、现在是什么状态？”**

这样以后数据库会舒服很多。

# 十四、Strategy Family 应该放在哪一层？

现在就非常好解释了。

它不在 Skill 下面。

不在 Team 下面。

也不在 Agent 下面。

它是：

> **Strategy 的管理 / 分类机制。**

```Plain Text
Strategy Library
│
├── DataAnalysis
│   │
│   ├── General Strategy
│   ├── Numerical Strategy
│   └── Statistical Strategy
│
├── Report
│   ├── General Strategy
│   ├── Academic Strategy
│   └── News Strategy
│
└── Planning
    └── ...
```

所以：

```Plain Text
Strategy Family
        ↓
Strategy
        ↓
Strategy Version
```

这个东西完全可以后做。
