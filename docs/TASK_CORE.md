**实现入口：** `evoteam/experiment_manifest.py`、`experiment.py`、`n4_campaign.py`、`scripts/run_n4_campaign.py`。**配置：** `examples/experiments/n4_comparison_v1.json`。**协议：** EXPERIMENTS §2.3–2.4。

- [ ] 核对配置中的 expected_model、数据引用、两个候选、Gate、最多 50 次请求；有模型或规则变化时先版本化方案并复核，不临时改参数追求通过。
- [ ] 在已提交且干净的代码上运行 `--preflight-only`；真实执行使用另一个新目录。

- [ ] 把 B 可用的 Run ID、快照/事件是否完整、候选与 Gate 引用一起交接，真实截图由 B 制作。

**验收：** 命令能复现流程，所有结果可追溯，不要求随机模型逐字重现。当前研究臂为预先指定，不能宣传成 Monitor 自动生成；当前两题 Validation 小于六题门槛，不支持晋级。本批 Final Test 评估未变更的服务策略。全部 Reject 或证据不足都是有效研究结果，但不等于完成正式演进收益验收。

## R2：补主场景评价与正式数据

**预计修改：** `domain/planning.py`、`evaluation/evaluator.py`、`tools/constraint_checker.py`、版本化 Prompt/Schema、实验数据和对应测试；接口改变同步更新 DEVELOPMENT 与 EXPERIMENTS。

目前 ProjectPlan 主要表达排期产物，Evaluator 的 success 是“Run 完成且没有规则错误”。清单中的合法不可行题可能必然无法产出合法排期，现有失败率不能直接当成“正确识别不可行”的准确率。正式基线前必须明确这个区别。

- [ ] 先为可行、因技能不足不可行、因预算/期限不可行、格式非法分别准备固定测试；明确每种情况应返回什么、由什么确定性证据判分。
- [ ] 在既定项目规划场景内设计版本化输出/评价契约，使“成功生成合法计划”和“正确识别无法完成”可分别报告。不能只采信 Agent 自述不可行；没有确定性支持的情况保持未知。旧 v1 记录与指标语义保留，不原地覆盖 Prompt。
- [ ] 扩充 History/Validation/Final Test，覆盖资源、依赖、期限、技能、预算和合法不可行；记录复核依据。不能仅改 ID、指令或随机扰动数字就宣称独立多样样本。
- [ ] 在新增验证结果出现前登记样本量依据、独立任务数、重复次数、失败/未知处理、验证复用上限和候选选择规则。六题只是现有研究门槛，不是统计充分性的证明。
- [ ] 基于新的 v0 基线提出正式 Monitor/Gate 版本，负责人审查后冻结；运行自动 Manager 及后续新任务验证。只有真实 Trigger、合法候选、独立验证和 Gate 都满足才晋级。
- [ ] 对真实结果交付“发生了版本变化”或“未满足晋级条件”的证据；没有晋级时不伪造未来收益。已使用的 Final Test 不用于反复选择新版候选。

**验收：** 同输入、同模型/Tool/预算、同评价器版本对照，正确不可行与执行失败分开，独立任务和重复运行分开；版本变化与未来任务影响可追踪。不能将研究对照脚本替代自动演进链。

## R3：崩溃恢复与运行预算（后续排期）

**预计涉及：** `storage/sqlite.py`、`evolution/manager.py`、CLI、Runtime 预算控制及故障注入测试。

交付内容：只读恢复诊断；核对进程已停止和已有封存/候选/Gate 后进行可审计恢复；清理操作幂等，不重发状态未知的模型请求。测试在候选前、验证中、Gate 后、事务提交前硬退出，以及重复恢复与并发恢复。不能无条件删除 claim 或把恢复解释为免费重跑。

预算需区分请求次数、输入预估、供应商实际 Token 与实际费用；说明哪些是请求前硬限制，哪些只能响应后检查，未知费用不转零。API 请求/超时/取消的返回和后台终态一致；不引入额外消息队列或微服务。

**验收：** 故障后可说明做过什么、哪些结果未知、为何可恢复；服务指针和审计一致，未确认终态不重复调用。

## R4：Tool/Skill 与受限能力（后续排期）

先登记固定工具的版本、输入输出、授权、超时、调用上限和 Trace，再将已有 constraint_checker 接入 openJiuwen Adapter。复用现有检查器业务规则；基础 SDK/解析库优先复用成熟实现，不下载未经审查的 Skill 直接执行。

固定 Skill 是版本化能力资产，不是任意代码生成器，也不能扩大 Tool 权限。固定加载和调用验证通过后，再按白名单增加 Tool Policy 候选；Validator 允许受控的 Policy 差异，同时固定工具实现版本与总体比较预算。Role Pool 与 v0 默认配置不悄悄改变。

**验收：** 未授权调用、错误 Schema、超时、越限和 Tool 失败均拒绝或留证据；同任务可比较 Prompt / Tool / Verifier 的质量和总成本。具体注册接口在本项开工前设计，不预先搭大型动态插件市场。

## R5：贡献与归因（后续排期）

按同任务、同配置控制条件生成有限消融/反事实证据；验证 Origin、Control、贡献归因的准确性与不确定性。新增裁剪/条件启用能力时保持固定 Role 与授权边界，候选先验证再改变未来策略。不可将高发言量、高 Token 或一次回答效果等同于边际贡献。

**验收：** 可以解释保留/移除节点或边的证据，记录反例和消融成本；高影响或不确定结论不会直接推动晋级。

## R6：监控与自动生命周期（后续排期）

逐项实现质量下降、成本异常等已冻结信号；用基线校准窗口、最小样本、冷却和退化边界。将已有 Stable/Reopen/Rollback 状态方法接上明确证据规则，保持验证 Run 不进入线上窗口、不递归触发演进。

**验收：** Stable 停止主动搜索但继续服务；达到新证据门槛才 Reopen；上线后退化恢复到可用历史版本，Rollback 与拒绝未上线候选分别留档。版本切换不改变在途 Run 的快照。

## R7：完整实验与补充场景（后续排期）

依 ROADMAP P5 补报告和数据分析的小型可复现任务套件、评价器及受控能力。补 Single Agent、固定多 Agent、Retry、无历史适配与 Mutation 消融对照，记录离线总成本和负迁移。前端仅消费真实字段，不在核心未实现时补造指标。

**验收：** 达到 PROJECT/ROADMAP 的完整范围；没有大量一次性脚本或仅漂亮页面就宣布系统完成。
